# AddRmsNorm 的跨核 rstd 写回

完整 BF16 合同计算残差和、逐行均方倒数平方根和带权输出。库调用为 `aclnnAddRmsNorm`，两个 BF16 输出再加一个 FP32 rstd。旧模型用 9 行窗口估计固定控制时间，少核时把部分多核争用带入首发，高并发时又漏掉 rstd 小写的等待。下表使用同一批旧窗只做开发回放。独立结果在下节另列。

| 950 SKU | 开发 shape | v2.4 WAPE / 最大 | v2.5 WAPE / 最大 |
|---|---:|---:|---:|
| DT | 13 | 18.85% / 36.03% | 11.05% / 16.18% |
| PR | 13 | 17.35% / 34.04% | 11.46% / 22.83% |

WAPE 用绝对微秒误差之和除以 CA 微秒数之和，最大值为最大绝对相对误差。旧版的十个留出 shape 已用于诊断。所有开发收据及最后一核 MTE3 发起/退休可在[开发账本](../../results/v2.5/add-rms-development.json)复算。

## 从 D 轴归约到整窗

1. 令 R 为 token 行数，D 为每行通道，C 为目标 AIV 核数。对整行能够放进 UB 的普通 BF16 路径，忙核连续处理 b = ceil(R/C) 行，共使用 A = ceil(R/b) 核。26 个开发窗的实测核数均与该式一致。宽度和行数影响单核的输入读取、平方和归约、逐行 rsqrt 和两张 BF16 结果的写回。模型沿用原有 Vector 两种可选定价和 UB 分块/重叠，仅补充尾部可见等待。[公共 Vector 阶段公式](../modeling-strategy.md)
2. 每行另写一个 4 字节 FP32 rstd。相邻忙核通常写连续的 4b 字节，若落在同一个共享写服务单元，可能排队。模型用 G = min(A, ceil(S/(4b))) 表示可能相互影响的写核数。S 的默认值为 128 B，是从相邻小写的规模和排队饱和区拟定的**有效争用范围**，目前没有微基准独立辨识它，也不能据此认定芯片的物理 cache line。
3. 设 J 为每个额外竞争写者的有效发起间隔（cycles），附加尾部为 (G−1)J。先在最后退休的忙核上找末个 RV 向量事件，再测至退休的差。单核的这个尾部在四个旧窗为 357～397 cycles。暂取 360 cycles 作为无争用参照。对 G≥4 的窗，把多出的尾部除以 G−1，各 SKU 取中位数，DT、PR 分别约 121、102 cycles；跨 SKU 共用圆整的 J=110。这个间隔综合包含写服务与排队，无法从这次记录进一步拆出仲裁和缓存代价。
4. 记 P 为原核内流水所需周期，H 为全芯片 HBM 有效载荷的周期下界，f 为 GHz。T = [L + max(P + (G−1)J, H)]/(1000 f) 微秒。首发 L 用两种单核宽度 1024 与 4096 的旧窗分别扣除载荷周期后取均值，DT 为 5162 cycles，PR 为 4764 cycles。未来芯片默认继承 DT 的周期参数，同时用其核数、频率、带宽及片上资源重排。可通过 chip.details 的 add_rms_fullrow_setup_cycles、add_rms_rstd_owner_cycles、add_rms_rstd_service_bytes 分别覆盖这三项。
5. 以 DT [32,2048] 为例，b=1、A=32、G=32，故附加 3410 cycles。同 shape 的 core0 里，4096 B 残差结果写的描述符窗为 338 cycles，相邻 4 B rstd 写为 4610 cycles，后续 4096 B Y 写为 4242 cycles。两条长描述符大范围重叠，直接相加会重复计等待。对照 DT 单核 [1,1024]，rstd 写窗仅为 102 cycles。当同核工作从一行变为多行时，4b 增大，G 下降，系统峰值带宽及单核归约仍各自形成约束。[各旧窗物理核级时标](../../results/v2.5/add-rms-development.json)

将 [32,2048] 代入上式，可沿控制、核内和共享链逐项复算。总读量为两个 BF16 输入加一个共享 BF16 gamma，共 266240 B；总写量为两个 BF16 矩阵加 32 个 FP32 rstd，共 262272 B。模型把共享的一次 gamma 读均摊到 32 个忙核，因此单核读 8320 B、写 8196 B。以每核 MTE2 48.36 B/cycle、MTE3 32 B/cycle 预算，读写各需 172.04 和 256.125 cycles。默认指令类方案按 64 个 FP32 lane 将单核工作换成 96 条读、129 条运算、32 条归约、1 条 rsqrt、65 条写、32 条谓词指令；总发起 355 条、双发射下限 177.5 cycles，在该例超过各指令类或端口下限。一页内三个阶段顺序衔接，P = 172.04 + 177.50 + 256.125 = 605.67 cycles。DT 的 H = (266240 + 262272) × 1.65 / 4000 = 218.01 cycles，于是 T = [5162 + max(605.67 + 3410, 218.01)] / 1650 = **5.562 µs**，CA 为 **6.544 µs**。PR 同形 P、G 相同，L 为 4764、H 为 622.89，预测 **5.321 µs**，CA 为 **6.136 µs**。这里的均摊 gamma 是逻辑流量约定，cache 命中、同一行被重复搬入和多个写描述符的依赖都会影响实际整窗。

仅对普通 BF16 gamma、非 Gemma 和能保守容纳整个行流水的 UB 配置启用该修正，整行判据为 24D + 1024 ≤ UB 字节数。24 B/元素为输入输出双缓冲和 FP32 中间量预留的近似，与实际 host 中包含多种暂存区的分块器有差别。其他精度、Gemma 预加一和需要 split-D 的路线保留原资源估计，CA 验证范围单列。普通 BF16 输出要求、行分区以及 key 1000/2000 与 CANNBot 950 的 pinned CANN 9.1 参考实现一致；本次 trace 来自安装的 CANN 9.2.1 二进制。

在已加载芯片及 feature 的常驻 Python 3.12 进程内，每个 SKU、每种模式循环查询 310 次，不缓存模型结果；两个 SKU 的默认模式 p50 约 93 µs、p95 约 105–107 µs。该墙钟属于 CPU 查询开销，图中模型/CA 的微秒数属于设备预测/设备事件整窗。[分模式主机查询记录](../../results/v2.5/add-rms-query-cost.json)

**误差还在什么阶段。** DT [63,640] 使用 63 核，末核 core22.veccore0 的最后一次 RV 到退休为 3394 cycles，模型给额外写争用 3410 cycles。PR [96,512] 使用 48 核，末核 core27.veccore1 的对应尾段为 1493 cycles，模型给 1650 cycles。这两种量的起止边界略有差别，但大小接近。两例整窗分别低估 17.07% 和 17.36%，单纯增大每次写等待不能解释这个偏差。以 DT [63,640] 为例，第一个 RV 读之前已走过 4751 cycles，首末 RV 的**经过时间**还有 2421 cycles，里面包含指令间隙和依赖。当前按吞吐定价的 VF 用量和固定控制时间无法单独重建这些间隔。PR [96,512] 末核的 8 B rstd 描述符和 2048 B 的 Y 写描述符分别持续 1558 和 1472 cycles，重叠退休同样构成真实约束。这里的载荷成本、描述符窗和 RV 经过时间不可直接相加。

**能否判断换芯片后的方向。** 以同一 shape 的 DT 时延除以 PR 时延计，10 个形状中判断正确的从 5 个增到 8 个。最有区分度的是 [63,640]，实测 DT 慢 43.5%，旧版预测约快 0.2%，加入 63 核与 32 核的不同写争用后预测慢 29.0%。错向的 [2,5120]、[96,512] 实测 DT 分别快 0.3%、1.9%，新版对这两个近等速点仍估为 DT 更慢。另一个误差来自多行的 [192,1536]，每核最多 3 / 4 行，实际 DT 慢 13.9%，新版仅估慢约 0.9%。这十种候选均命中安装包的 AddRmsNorm_bf16_high_performance_1000 整行内核，活动 AIV 数全部符合分区公式。未来 SKU 的表内耗时基于同样的行分区和共享写机制外推。
