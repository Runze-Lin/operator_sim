# 1　从系统问题到可验证的算子问题

## 1.1　系统排程器需要哪一个时间

考虑一个请求已有 128Ki 个历史 token，草稿模型又提议 8 个 token。目标模型可一次校验 9 个位置。注意力的 Q 行数很少，但一个头仍需处理很长的历史。相反，一个 32Ki 的 prefill 请求可能被切成多个 4096-token 块，每个块有许多可以并行的 query，靠后的块还要读取更长的历史。二者都可以被图捕获器叫作 attention；若只按算子名称套一个利用率，既不能判断一张卡上有几个头可分，也不能判断相邻 query 能否复用同一批页。

本文的基本输入是一次已经完成并行分片的本卡调用。TP 切哪些维、EP 将哪些 token 送往本地专家、每个 attention DP 副本打包几个请求，属于系统层。算子层接收实际 shape、输入和输出精度、布局及实现属性。对 routed MoE，已知时还接收每个专家的行数。对有状态或数据相关的调用，前序执行信息和候选页序列也是可选输入。缺少这些信息时，模型仍可在规定的假设下给情景值，其验证资格随输入而变。

输出有三种时间。设备时间从核开始到设备计算完成，系统用它占用执行资源。若系统还要模拟主机发起，可根据实际物理 kernel 数量另加配置中的开销。第三种时间是预测器在 CPU 上回答这次查询的墙钟开销，决定模拟一张大图要花多久。CA 仿真器在宿主机上生成数据库又是一次离线工作。一条 275 µs 的设备记录，可能需要长得多的离线时间才能得到；系统重放时只调用预测函数。

## 1.2　怎样定义「最理想」才有可比性

对给定的工作、引擎和内存层级，令 F 为运算次数，P 为同精度下相应引擎的每秒峰值，B 为必须经过受限接口的字节数，W 为该接口字节每秒。计算至少用 F/P 秒，搬运至少用 B/W 秒。令两者完美重叠便有时间下界 max(F/P, B/W)。若有互相独立的 Cube 与 Vector，再分别列出两个计算项，取最大。这个推导要求每一项的工作确实在所比较的计时窗内完成，并且吞吐上界与指令匹配。Roofline 文献把运算强度与可达到的性能联系起来，恰好提供这种约束。[Williams 等，2009](https://doi.org/10.1145/1498765.1498785)

实际应用有两处容易混淆。第一，MXFP4 权重可以以四位存储，再被展开到八位参与乘加；若按存储位宽选 Cube 峰值，算术下界偏小。第二，张量逻辑输入和输出不一定在设备指令窗口内全部穿过 HBM，请求可能由 L2 满足，写回可能延后。相反，读写描述符也可能因分块而重复加载同一个逻辑张量。于是逻辑字节除以 HBM 带宽可以是系统设定的冷读写场景，却不能单独证实该窗内的物理 HBM 流量。

为了给系统开发者一个易读的参照，定义等效 U 为同合同的理想参考时间除以预测时间。U 很小可以由单行只启用一个核、工作达不到饱和、同步或首发占比高引起。U 大于一时应先查分子和分母的边界。发布的原始诊断保留越界值；在需要完整冷读写的系统场景中，节点完成时间至少要覆盖该策略的读写义务。附录与逐窗页保留两者。这样既能检查假设，也能防止把一个已由模型施加的下界当作独立准确性证据。[口径与反例](../roofline-audit.md)

## 1.3　哪些结构应当迁移，哪些量需要重算

用一个矩阵积说明分层的意义。矩阵的有用乘加为 M×N×K；矩阵引擎可能还要补齐边界，依次读取若干 K 页，将中间结果保留至最后一页。换卡后，数学上的有用乘加不变，但是较大的缓存可能改变页数、不同数量的核可能改变尾波、单核发射能力与 HBM 总带宽则改变每页的服务时间。因此只乘一个整片峰值之比会同时遗漏并行度和数据重用。有些形状反而应继承几乎相同的周期数，例如只给一个头排任务、循环节奏受单核控制发起约束的情况。第 3 至 5 章分别给出推导、校准和换卡实验。

将资源和映射作为两个可替换的对象，也是加速器建模的常见思想。Timeloop 从计算映射和数据复用分析资源代价；本文进一步利用实际 kernel 的指令时标检查所选排程。FlashAttention 对分块读入 K/V、维护在线 softmax 状态的分析说明了同一数学结果可以对应不同搬运量。其论文并未给出本研究昇腾 kernel 的发起周期，本文的周期来自独立标明的 CA 数据。Uni3Sim 的 910B 微基准启发了有限轮数和逐级交接的测量设计，特别是将首次完成与下一次可发起区分开来。第 4 章使用 950DT 自身的记录估计数值。[Timeloop](https://timeloop.csail.mit.edu/) · [FlashAttention](https://arxiv.org/abs/2205.14135) · [Uni3Sim 固定版本](https://github.com/thu-nics/uni3sim/tree/52ffdb18aef705b03e27534ddd999312a9ec5ca2/microbench/ascend_910b)

## 1.4　一条证据如何从库实现走到系统结果

实验先保存实际库入口、kernel 名、精度、shape、芯片与运行次序，再检查完成标记和工作范围。库源码能够说明为什么可能出现某种指令；实际安装包发出的 trace 才能确认本次运行选择了哪个分支。从可对齐的事件读出局部服务量、有效负载、间隔及末核结束时刻。冻结参数后再看新形状，最后将可用路径放回原图按依赖重放。源代码中的数学意图、冻结前的误差、冻结后的偏差、系统反事实和 970DT 无实现外推各回答不同的问题。

本文依次回答四件事。怎样从算子输入推导每核工作？怎样把各阶段的周期合成为一个物理窗口？哪些周期可以在开发数据中单独识别？当目标芯片尚无实现，哪些结论对资源变化稳健？读者可以先复算第 3、4 章的同一个注意力例子，再用第 5 章改变一项芯片参数，这三步对应从可观测证据走到有条件外推的完整过程。
