# Flash 候选 Indexer 在 27 组系统配置中的影响

## 单轮时间的计量方法

实验复用上一轮的 27 份 task.toml 和带相同 950DT 硬件配置的系统环境。原 Roofline、v1.7 混合后端及新增 Indexer 的混合后端分别从 preset 重新捕获 target、draft 并执行 DES，每个后端各跑 27 个任务。纯 Roofline 的三种设备时间（target、draft、整轮）、图与输入指纹和峰值显存均复现归档。各并行布局的 Flash 节点本卡 Q 都是 9、H 都是 32、D 都是 128，target 和 draft 的 L 分别为 131,081 和 131,090。B=1/16/64 对应 9/144/576 行 query，工作量随 B 改变。每个 B 对应单卡请求数，一轮包括两个阶段各一次，不含多 rank 同步、宿主采样与服务调度。三条路线共享同一组缺价和占位项。整网真机误差需要独立的设备测试。[输入、计时和显存口径](sim-platform.md#九组配置的比较条件)

脚本核对每个任务的公共图与输入指纹、单卡静态峰值、节点顺序、阶段、预测来源、价格及总时延。v1.7 的逐轮、逐阶段耗时必须复现冻结的 1.7 表，每一个非候选 Indexer 节点必须复现旧混合后端的预测来源和耗时。覆盖率采用同一批形状的**原 Roofline 时间加权**，分子为已接管节点的原 Roofline 时间，分母为全部原已定价时间 4,814.851 ms。这个定义允许比较两版的覆盖，与迁移后该节点占新预算的比例分别计算。[冻结的旧表](../calibration/reference/system-decode-compare.csv)

27 组共捕获 171,232 个节点，98,920 个进入成功定价分母。其余 64,365 个由平台标记为零开销而跳过，6,078 个是占位，1,869 个缺价，例如任务未给通信参数的集合通信。三种后端的这些项目均取相同的系统预算。

以 Flash TP8/EP8、B=1 的 target 图节点 2636 为例，它包含 9 行查询、32 个 head、维度 128、每请求 131,081 个 key 位置和 2,048 个候选槽。旧后端将 `2 × 9 × 32 × 128 × 131081 + 9 × 2048 = 9,664,358,400` 次操作全部分到 FP32 Vector。系统预置的有效 Vector 吞吐为 `16 × 0.6 = 9.6 TOP/s`，因此 Vector 项为 1,006.704 µs，逻辑读写的带宽项为 10.539 µs。旧账本取其中较大的 1,006.704 µs。算子的全表打分、实际候选过滤与实现证据见[逐算子推导](examples/candidate-filtered-indexer.md)。

## 三方同图结果

按原 Roofline 预算加权，27 组整体覆盖率从 **37.14% 升至 67.63%**，其中 Flash 九组从 **21.93% 升至 88.15%**。在同一个 4,814.851 ms 分母上，接管的预算由 1,788.289 ms 增至 3,256.097 ms。新增 54 个外推节点，新后端共接管 47,874/98,920 个成功定价节点。新增的 30.49 个百分点全部来自候选 Indexer 的融合排程外推。新接管的节点中，与该融合实现和系统形状匹配的完整 CA 时间窗为 **0/54**。950DT/PR 上已有的小规模分解路径实验及具体形状见[算例](examples/candidate-filtered-indexer.md)。

每个模型各有九个配置。下表时间为这些独立配置各执行一轮的总和。

| 模型 | 原 Roofline ms | v1.7 混合 ms | 新混合 ms | 按原耗时加权的接管比例 v1.7 → 新版 |
| --- | ---: | ---: | ---: | ---: |
| V4 Pro | 859.311 | 883.174 | 883.174 | 45.88% → 45.88% |
| V4.1 Flash | 2,216.538 | 2,418.165 | 1,015.676 | 21.93% → 88.15% |
| Kimi K3.1 Pro | 1,739.003 | 1,838.418 | 1,838.418 | 52.22% → 52.22% |
| 全部 | 4,814.851 | 5,139.758 | 3,737.268 | 37.14% → 67.63% |

以 TP8/EP8、B=1 而言，四次 target 的新版单次预测均为 422.971 µs，两次 draft 均为 422.997 µs。旧回退把点积全部记在 Vector。新版假设 BF16 点积在 Cube 上执行，由 Vector 归约、筛选并产生排序索引，两者读取同一张完整 key 表。这一排程变化解释了方向。是否能实现预测差距还需要匹配部署实现的整窗计时。

Pro 与 Kimi 共 18 个对照任务没有这条候选节点，逐节点比较和两阶段 DES 均复现 v1.7。27 组静态峰值逐组相同，节点定价失败数为零。各次执行仍保留原有缺价和占位。[全部 27 组时延、覆盖分子及分母](../calibration/reference/system-candidate-comparison.csv)

## 重跑与核对

使用包含本仓 `operator_sim` 插件的 preview 系统运行时。在本仓根目录设置 `MATRIX` 为归档目录 `experiments/decode-950dt-128k`，`SCRATCH` 为独立输出目录，`REFERENCE_WHEEL` 为由提交 `0fe1e42` 生成的工具 1.7.0 wheel。本次回放已核对该 wheel 中 `operator_model/` 的每份文件与该提交一致。第一条命令使该次测试进程优先导入冻结 wheel，候选模型运行从当前安装的精细后端读取模型。仓库保存紧凑结果，本地 scratch 保留每个节点的压缩对照账本。

本表使用 v1.8 融合排程，其 `candidate_indexer.py` 的 SHA-256 前缀为 `c2e9c243522d`，系统适配层为 `4df2c9cef17b`。CSV 中的 `*_us` 是单卡设备模型时间，`*_wall_s` 是各次系统仿真的宿主墙钟。

```sh
PYTHONPATH="$REFERENCE_WHEEL" python -m calibration.system_candidate_compare "$MATRIX" "$SCRATCH" v17 --jobs 6
python -m calibration.system_candidate_compare "$MATRIX" "$SCRATCH" rank
python -m calibration.system_candidate_compare "$MATRIX" "$SCRATCH" candidate --jobs 6
python -m calibration.system_compare "$MATRIX" "$SCRATCH" roofline --jobs 6
python -m calibration.system_candidate_compare "$MATRIX" "$SCRATCH" compare --fresh-roofline
```
