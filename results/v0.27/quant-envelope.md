# Kimi-K3 整批预填充的 MX 量化流量与时间

B8 × 32 Ki、不切 chunk、hidden=7168 时，混合 QKV 在 MXFP8 动态量化、`scale_alg=0` 的分支可独立调用 `aclnnDynamicMxQuant`。950DT 一次运行的 64 个 AIV 从最早启动到最后完成共 **1778.988 µs**。默认预测 1200.415 µs（相对包络 -32.52%），显式资源模型 1394.986 µs（-21.59%）。以配置的 4.000 TB/s 为准，原生通道记录支持两者低估所需的总线服务时间。按 CA 引脚配置计算 4.096 TB/s 后，只有默认值仍低于实测流量下限。该形状的标准逐指令延迟仍为 N/A，这些偏差不计入指令窗 WAPE。

## 实际使用的字节与窗口

- 输入 BF16 `[262144,7168]` 有 3,758,096,384 B。FP8 值有 1,879,048,192 B。每 32 个通道产生一个 E8M0 scale，按每行两字节打包后的大小为 `2 × rows × ceil(cols/64)`，本例为 58,720,256 B。两个输出逐元素核对，共 1,937,768,448 个值、0 错。热态、输入复用、脏行延迟写回均可使调用窗口中的 HBM 字节与这 5,695,864,832 B 有别。
- 原生窗口取 64 个 AIV 的最早 start 9,789 tick 到最晚 done 2,945,120 tick，除以 1650 tick/µs。末核为 `14.2`（物理 core.子核）。复验全套 64 个 block ID 与两个 golden。大例保留的是原生核汇总，无法从中提取逐 tile 的指令时序。
- 原生模拟从启动到最终控制器报告共 1786.333 µs。128 个通道各自登记完整的 32/64/128/256 B 读写事务数。各尺寸乘实际字节后求和，精确对上已归档的 DMC 与 DDR 两个总计。不能直接将读写命令个数乘一个固定常数。

| 跨全部通道 | BF16 输入 / 两个输出逻辑 B | DMC 全进程 B | 相差 B |
|---|---:|---:|---:|
| 读 | 3,758,096,384 | 3,763,522,944 | +5,426,560 |
| 写 | 1,937,768,448 | 1,888,006,144 | -49,762,304 |
| 合计 | 5,695,864,832 | 5,651,529,088 | -44,335,744 |

DMC 全进程的实际平均吞吐为 **3.164 TB/s**，占芯片配置峰值 79.09%。按逻辑字节除以原生 wrapper 的算法吞吐是 3.202 TB/s。两者均含空闲和控制阶段，无法从全程平均值反推 MTE 发起间隔。

即使不假设两种时钟原点相同，只要 wrapper 位于同一次控制器采集期间，长度为 $W$ 的 wrapper 在长度为 $D$ 的采集内的任意位置均覆盖 $[D-W,W]$。向内取完整 1 µs 控制器采样区间，得到 [8, 1778] µs。其间确有读 3,762,442,112 B 与写 1,887,600,128 B。它们覆盖全进程字节的 99.974%。这是 wrapper 时间范围内的全通道事实，仍含同一进程中的元数据及可能的背景流量。无法把余下时间或任一字节归给具体 tile。逐区间哈希和末期事务分布列于 [JSON](quant-envelope.json)。

## 哪一条下界成立

令 $R$、$W_b$ 为输入和输出字节数，$C$ 为共享 L2 容量，$B$ 为读写合计峰值（GB/s，十进制）。任意指定穿过该端口的 $Q$ 字节最少占 $Q/(1000B)$ µs。选择 $Q$ 需要说明缓存起止状态和测量边界。

| 950DT 的前提 | 纳入的字节 | 以 4.000 TB/s 计的下限 µs |
|---|---:|---:|
| 输入已冷且结果全写回 | $R+W_b$ | 1423.966 |
| 输入已冷，最终允许最多一份 L2 写缓 | $R+\max(0,W_b-C)$ | 1390.412 |
| 初始允许缓存输入，退出又允许缓存输出 | $\max(0,R-C)+\max(0,W_b-C)$ | 1356.857 |
| 同一次 CA 中、wrapper 必含的完整报告区间 | 5,650,042,240 B | 1412.511 |
| 完整控制器运行 | 5,651,529,088 B | 1412.882 |

容量两式假设唯一数据的可跨调用留驻储存由 L2 代表，并限定相同地址空间的单次独立调用。若系统把输入和输出留在其他缓冲区、与上下游融合、改变写策略或 HBM 另有独立读写通道，需重新编写下界。按未知驻留的容量下界，资源模型通过，默认预测仍偏低。全进程额外捕获的时间不能补入标准指令窗。

每份通道原始头是 `hbm3 8000Mbps, x32`，理论引脚和 $128×32×8/8=4096$ GB/s。芯片配置取 4000 GB/s。引脚和值还未扣除总线转向、刷新及协议成本。使用引脚和，完整控制器服务下限下降到 1379.768 µs，必含区间为 1379.405 µs。依据量化单次运行无法断定配置口径与 CA 控制器绝对峰值完全等价。

| 模型 / 实测 | 时间 µs | 逻辑流量 / 时间 TB/s | 整体 DMC 流量 / 所列时间 TB/s |
|---|---:|---:|---:|
| 默认 | 1200.415 | 4.745 | 4.708 |
| 资源 | 1394.986 | 4.083 | 4.051 |
| 原生 wrapper | 1778.988 | 3.202 | 3.177 |

表中不同时间作为分母仅用于比较，实测的全进程平均带宽在上一节给出。

## 资源模型中的误差来源

此形状的 950DT 默认路由沿用参考预测器。用目标芯片资源重算时，分核为 64 AIV，最忙核 4,096 行，UB tile 为 [5,7168]，共 820 轮。资源模型已经限制独立 MTE 与共享带宽，读侧取 3,758,096,384 B。由于预留活跃核的两块输入 tile，估计退出时仍有 125,042,688 B 输出可留 L2，写侧仅计 1,812,725,760 B。实际 DMC 读比模型多 5,426,560 B、写多 75,280,384 B。按配置峰值换算，这两项差额共 20.177 µs。即使把控制器实际总量作为带宽服务成本，其理想下限至 wrapper 仍有 366.106 µs，涉及管道执行、请求效率、内存调度和 wrapper 边界，无法只归因为一个固定 launch 或一个输出留驻比例。

真实 64 个 AIV 各自的忙周期占自身 wrapper 的中位数分别为 MTE2 98.5%、MTE3 60.7%、SIMD 53.9%。同一时段可以多条流水同时忙，三项不能相加。这些汇总无法重建逐指令关键路径。若需将差距下推至系统仿真，可按是否预热、是否要求落 HBM 进行情景计算，并让目标芯片的共享口径、实际并发和分块决定可用吞吐。本次 79.1% 仅描述本次离线运行。

## 两个采集控制与历史回放

以下两形均运行 950DT 的 BF16→FP32 Cast。它们核验相同原生采集流程的窗口定义，其中 [262144,32] 留有同次运行逐核边界对照。不同算子和数据驻留使控制组差值无法直接用于量化窗口的校正。

| Cast shape | AIV | 完整指令 µs | wrapper µs | 差 µs | DMC 读 / 写 B | 全冷读且全写回下限 µs |
|---|---:|---:|---:|---:|---:|---:|
| [32, 4096] | 64 | 2.771 | 4.899 | 2.128 | 307,072 / 0 | 0.197 |
| [262144, 32] | 64 | 9.970 | 12.267 | 2.298 | 16,822,272 / 0 | 12.583 |

[262144,32] 的输入输出合计不足 L2，wrapper 时间也短于逻辑冷读全写回线。原生控制器记录 0 写。这给出了把每次逻辑写入都算作窗口内 HBM 流量的直接反例。两个控制组的 wrapper 分别比标准窗口多约 2 µs，无法为跨算子的时间差规定严格上界。

v0.27 的已核验量化开发回放采用官方核第一条指令到设备最后一条指令的时间。在同一批历史 shape，离线试算条件下界。若 $R+W_b>C$，延迟取默认预测与 $(R+W_b)/(1000B)$ 的较大值。另统计更严格的读、写各自都大于 L2 的样本数。正式历史回放和上面单个大 shape 的 wrapper 各自统计。

| 950 SKU | 指令窗数 / 不同开发形数 | L2 MiB | 最大逻辑流量 B | 合计超 L2 / 两者各超 L2 | 默认改变数 | WAPE 原值→试算 |
|---|---:|---:|---:|---:|---:|---:|
| Ascend950DT_9582 | 59 / 58 | 128 | 31,784,960 | 0 / 0 | 0 | 4.74% → 4.74% |
| Ascend950PR_957b | 53 / 53 | 112 | 31,784,960 | 0 / 0 | 0 | 7.71% → 7.71% |

DT 的 [4,256] 有两个不同指令窗。WAPE 以归档窗口计算。两端最大同为 [2048,5120]。这组开发回放没有覆盖规则会启动的区域，所以零变化无法证明跨 L2 后的准确性。大形只有 950DT 的一次原生窗口，且属于回顾性诊断。在该大形上强制冷读全回写，默认和资源结果都将变为 1423.966 µs，距离原生窗口仍低 19.96%。950PR 同形和 970DT 均未有 CA 窗口。

| [262144,7168] | 峰值 GB/s | 默认 / 资源 µs | 未知驻留 / 冷读全回写线 µs | 原生 wrapper / 标准指令 µs |
|---|---:|---:|---:|---:|
| Ascend950DT_9582 | 4000 | 1200.415 / 1394.986 | 1356.857 / 1423.966 | 1778.988 / N/A |
| Ascend950PR_957b | 1400 | 3992.864 / 3992.864 | 3900.703 / 4068.475 | N/A / N/A |
| Ascend970DT | 14400 | 527.779 / 527.779 | 367.768 / 395.546 | N/A / N/A |

950PR 的 1.4 TB/s 是芯片配置按 SKU 档位推得的值。970DT 的 14.4 TB/s 来自用户情景。其 120 AIV 的 MTE 与 UB 细节沿用 950 假设。这两行只描述参数敏感性，未验证跨芯片加速比。当前证据支持优先核对大形默认路由，并在有独立超 L2、不同读写比例的指令窗后再决定条件规则。单次观测无法识别可迁移至后续芯片的单一效率。
