# 为四个已冻结的 CA 作业分配宿主资源

四个作业沿用 v0.25 登记。Cast [851968,32] 和 Sigmoid [1703936,12] 各在 950PR、950DT 运行一次，各自的逻辑读写量均为 156 MiB。原监督进程一直持有排他锁，等待 Pro 和 Flash/Kimi 全部结束。这份补充只替换每个作业启动前的宿主准入条件。[冻结的输入、预测、ELF 和预算](../../v0.25/cache/freeze.json) · [实时负载和阻塞原因](state.json) · [原始采集状态及最终回执所在目录](../../v0.25/cache)

**交接。** 2026-11-19 17:19 UTC，两次核实 PID 2528633 的命令行、启动时标、原排他锁、正在 nanosleep、无子进程，四个原 raw 和回执均尚未创建，旧启动条件的两个先决作业均未完成。通过 pidfd 只终止该空等 Python 进程，新会话 operator-sim-cache26 接手同一文件锁。采集、解析、计时资格、输出、预估和失败处理仍由原始 campaign.run 执行，原代码和原冻结的 19 项输入均通过 SHA 复核。[交接前的八项核对](handover-preflight.json) · [旧/新 PID 与锁](handover.json)

**准入条件。** 每隔 15 秒读取宿主负载和 /proc/stat 实际空闲 tick。以下条件连续满足 180 秒才启动一个作业。作业之间重新计时。Pro 正在等自己的启动窗口、FA 正在等资源、或 Kimi 已退出而 Flash 尚未启动时，都优先给先登记的作业。正在运行的 Kimi 与 Pro 保持原排程。

| 项目 | 256 物理核宿主的门槛 |
|---|---|
| 1 分钟 / 5 分钟负载 | ≤161.28 / ≤179.20 |
| 最近一个采样间隔的空闲 CPU | 总量至少 89.6 核，所选掩码内平均空闲率 ≥64% |
| 主机内存 / 可用磁盘 | 均 ≥128 GiB |
| 文件脏页与回写量合计 | ≤16 GiB |
| 单例资源 | 所选 112 个近期最空闲物理 CPU、SCHED_IDLE、nice 19。一条待运行的 CA，全部子进程从同一宿主继承。原作业的超时为 90 分钟、raw 限额为 16 GiB。 |

112 是实际 affinity 的 CPU 数上限；Linux 的 SCHED_IDLE 优先级让正常调度类的工作优先。该设置不保证已启动的 CA 每秒都有固定 CPU 配额。原始对照所耗 CPU 时间约 19,146–59,797 秒。以前 102 个原生线程被固定在 16 个 CPU 上发生控制窗超时，因此本轮给线程较宽的可选集合，并在入场前预留 CPU、内存和落盘空间。作业启动后不抢占或暂停 CA；如果并发环境随后变差，则保留原限额及失败回执。[准入参数与九个对照的成本](admission.json) · [以往窄 affinity 对照](../../v0.23/full-hidden/v3/registration.json)

准入通过时会另存每项实际 CPU 掩码、nice、调度类、当时负载和资源。四项都在原 results/v0.25/cache/raw 的排他锁内按原顺序运行。若原进程异常留下未完成 raw，原程序会保留现场停下。当前没有 ROI 或计时指标可从排队时长推断。

在该主机的仓库根目录可运行以下命令恢复已交接的监督进程。命令会先复核原冻结文件及排他锁；已有会话运行时会直接遇到排他锁，不会双跑。

~~~bash
MPLCONFIGDIR=/tmp/mpl-cache26 toolchains/envs/cann-9.2.1/bin/python development/validation/cache26/guard.py run
~~~
