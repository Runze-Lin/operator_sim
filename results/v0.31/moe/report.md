## 旧 trace 如何验证实际工作

保留 10 个专家分布不同的旧 shape，在两个芯片上各自复查 GMM1 和 GMM2，共 40 个完整的子算子窗口。本次沿用原宿主的三个 golden 检查。GMM1 的 ACLNN 入口是 `aclnnGroupedMatmulSwigluQuantV2`，GMM2 是 `aclnnGroupedMatmulV5`。官方 msopprof 采集逐核读 `trace.json`，历史 DT 的 npusim 池逐核读 `ExecutedInstructions`。每条记录保留所属的原始采集链路、kernel 名和哈希。相同 shape 在两端有不同采集方式时，执行差别仍可能受该因素影响。[原始计时与 golden 回执](../../v0.17/sku/pairs.json) · [逐端证据](mx-audit.json)

## 从小模板到大形预算的计算

在这次 DeepSeek-V4-Pro 的几何示例中，B8 × 32 Ki token，top-6、均衡 EP384、专家内部 TP8，得到 T=4096，K=7168，F=384，E=1。当前 CANN 路径的矩阵/scale 类型是 MXFP8/E8M0；模型原生专家权重 FP4，通信和路由耗时应另计。[形状推导与 dtype 范围](../../v0.29/large/cube/freeze.json)

对于一个专家，DT 参考模型令 `W=ceil(ceil(T/16)×ceil(N/128)/32)`，`U=W×ceil(R/64)`。N 是输出通道数，R 是归约长度。GMM1 的 (N,R)=(768,7168)，故 W=48、U=5376。GMM2 的 (N,R)=(7168,384)，故 W=448、U=2688。W 是逻辑波数，U 是归约工作单位。上表实测的 m、n、k 和有效核数说明，二者不能直接当作实发指令数或真实分核。

每个小模板将设备时间切成队列活跃集合固定的区间。设区间原始长度为 d，活跃队列集合为 S，则模型定价 `d × max(q∈S, 大形工作量[q]/模板工作量[q])`。SCALAR 和空闲的工作量取 W，MTE2、MTE1、CUBE 取 U，同时活动的区间采用最慢队列对应的倍数。即使是最早的标量准备或第一块的输入填充，也使用同一缩放规则。这是代码中可验证的价格行为。[实际实现](../../../operator_model/fusion_v8.py)

逐模板读源数据库，在每个核域选择模板记录的末核，按原始事件顺序重放上述公式。先以模板全芯片最早 MX 划一条时间线，再分别积分之前和之后的模型价格，选择总时延最大的核域。四个模板取中位数，本例中为中间两个候选的均值。两段都复原了公共 API 的 DT 价格，未改参数。[候选、源 DB 哈希、倍率与首发前金额](mx-audit.json)

| DT 阶段 | 两个中间模板的首发前原始 µs | 首发前区间投到大形 µs | 大形阶段总预算 µs | 占阶段预算 |
|---|---:|---:|---:|---:|
| GMM1 | 5.685 / 5.618 | 2753.35 | 5758.66 | 47.8% |
| GMM2 | 2.862 / 2.575 | 1708.51 | 2390.96 | 71.5% |

两段预测 8149.62 µs 中有 4461.86 µs（54.7%）出自该区间。这个数字度量了总价对小形首发前排程的依赖，其中也有随载荷增长的取数。直接扣掉它会同时删掉部分真实工作。首发、稳态和尾排的真正比例需要大形完整 trace 识别。

## 与硬件极限、当前大形采集对照

满芯片 FP8 Cube 下界 `T_C=有用矩阵 FLOP/(FP8 TOPS×10⁶)`，单位 µs。冷数据一次读写时间 `T_H=(逻辑读+写字节)/(HBM GB/s×1000)` 取十进制 GB/s，假设每个逻辑字节均跨 HBM 总线一次。缓存命中、重读和中间写回会改变 HBM 流量。各阶段分别计算，再串行相加。峰值与模型可达到的持续速率存在差异，本表的倍数不能当作 CA 误差。

| 芯片 | 阶段 | 公开预测 µs | 满芯片 Cube 下界 µs | 冷数据单次读写 µs | 公开预测 / Cube 下界 |

| 950DT | GMM1 / GMM2 | 5758.66 / 2390.96 | 52.14 / 26.07 | 9.39 / 15.80 | 110.5× / 91.7× |
| 950PR | GMM1 / GMM2 | 6570.86 / 2581.78 | 59.65 / 29.83 | 26.84 / 45.13 | 110.2× / 86.6× |
| 970DT 外推 | GMM1 / GMM2 | 1620.21 / 1372.23 | 12.74 / 6.37 | 2.61 / 4.39 | 127.2× / 215.4× |

大形首段的已落盘调度日志显示 task 0 派发 32 个 AIC 主块与 64 个 AIV 子块，kernel 对象 SHA256 与 DT 的 [2,64,64,1] 同包对象完全一致。相同二进制允许走不同 tiling 分支，这次派发不能证明每个 AIC 都实际发了 MX。快照时只见首段启动和进度信息，完整指令窗、第二段、三组 golden 均待回收。[有界只读快照](dispatch-snapshot.json)

判别大形机制需要同一回执同时给出两段的整窗与正确性、逐条 MX 尺寸与逐核命中、首发/相邻发起间隔分布，以及末核的 MTE2、CUBE、FIXP 与 GMM1 AIV 写回关系。先用尺寸检查 FLOP 守恒，再把核内首个 tile 的填充、后继 tile 的稳态和最后写回分别定价，才能区分错误分块、重复计首发和资源吞吐差异。现有小形可验证工作量和指令识别，尚不能识别大形稳态或支撑新的跨代时延参数。本次未新开 CA，所列样本均为历史开发回放。[复算程序](../../../development/validation/moe31/audit.py)
