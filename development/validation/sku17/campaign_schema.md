# Paired CA campaign

`extension-freeze.json` and `core-freeze.json` record model parameters, actual host hashes, exact case arguments, assets, budgets and all three device predictions before opening the new labels. The extension and core freezes are separate. Extension capture used the earlier unchanged extension implementations; current release predictions are checked against the freezes.

`records.json` is the long table (one device/shape/attributes/operation per row). `pairs.json` joins only qualified timings on both sides. Speedup is DT time divided by PR time. `backend_match` identifies matching CA capture tools; it does not prove identical cache state or dispatch before a measured kernel. The first case in each extension host route is used as an additional same-host/same-argv MSOpProf DT control where available. Historical CA artifacts retain their native scope and provenance; cross-tool pairs are comparisons of qualified measurements, not proof that the tools agree. A chain is the sum of its serialized per-kernel windows, excluding host launch gaps. Peak active core counts do not sum across launches. Chain components and chain totals share captures; do not add all component/chain costs or count them as separate launches.

Qualification requires the exact runtime SKU and memory model, all requested host golden checks, successful simulator and parser, complete per-core windows and agreement with the corresponding vendor table. For multikernel applications, use the launch name / same-name launch ordinal to address the exact trace directory and the corresponding table by launch order. Missing timing or incomplete/synchronization-failed captures never have an error of zero. KDA chunk is a structural route with no numerical estimate unless timing becomes independently eligible.

`all-costs.json` counts physical attempts, not logical rows. The `cost` repeated per logical row links it to the physical attempt. Capture CPU excludes unaccounted CPU in process-group timeout cases. New DT control cost, recovered attempts and failed attempts are included. `rejections.json` retains failed physical attempts even when a retry succeeded.


Worker scheduling: one host has 256 logical CPUs. During one mixed batch, 11 simultaneous 32-thread CA instances oversubscribed the simulator and six cases exceeded their configured wall caps. The additional DT controls and core dispatcher were temporarily paused (existing child simulators completed). The balanced dispatcher filled at most two new core slots alongside five extension slots, later five core slots after extension completion. No model changes or replacements chosen on numerical error. Original failures remain in the cost ledger; infrastructure retries use identical predictions/host/argv and the original per-case cap. For completed attempts with reporter lag, elapsed time in the normalized ledger is the interval from launch to GNU time's process-exit file, not the scheduler's later observation.

The KDA chunk PR probe uses the host in `scripts/cube-v8-kda-safe.cpp`. Its call to `aclnnChunkKdaFwdGetWorkspaceSize` uses safe-gate lower bound −0.03125, requests final state, GK, QK and KK, and has six checks including unchanged input state. The original frozen structural request omitted `safe_gate`, `lower_bound` and `export_gk`. `rejections.json` records both contracts and the actual simulator failure. No paired timing, speedup, or error is reported for this path.

`campaign-completion.json` is emitted after each original, control and registered retry has a terminal cost. It audits each input's frozen DT, PR and future forecast against the final model, checks that every pair has the same input contract on both ends, and records outstanding timing gaps. Its file digests identify the final suite. Device latency is in microseconds; offline CA wall and CPU costs use seconds. Cases sharing one serialized launch do not incur duplicate physical collection cost.
