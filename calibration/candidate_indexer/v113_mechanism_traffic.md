# 旧 QSLI 窗的 544B 候选读取

950DT 与 950PR 的 Q32 输入、候选序列与 folded 读描述符数完全相同。在 DT 上，96.11% 的读取与另一个团队对同一 record 的读取落在同一个 128 周期桶中；在 PR 上为 7.59%。这为前述 metadata 分核导致地址发起相位不同提供了指令级依据。DT Q64 的第二行在更高的同址比例下发起得更快，说明还需要考虑行间预取与环形流水的运行阶段。

## 指令、时钟与口径

对每个 AIV 的完整设备指令 trace，取 `MOV_SRC_TO_DST_ALIGNv2` 的 OUT→UB、burst 长 544B 的描述符。双 burst 使用实际地址步长拆成两个 record，两者属于同一发起刻度。两个伴生 AIV 属于同一团队。在 1.65 GHz 下，128、512、2048 周期分别约为 0.078、0.310、1.241 µs。所有桶锚定全设备首条指令，读取按发起刻度分桶，跨过桶边界的相邻事件可能落入不同桶。每个数字都能从已有原始目录重算。[提取代码](v113_mechanism_traffic.py) · [完整计数与三种桶宽](v113_mechanism_traffic.json)

| 已有窗 | 发起 record 总数 / 唯一 record | 整段发起密度（record/周期） | 每 512 周期 record 数 P50 / P90 | 128 / 512 / 2048 周期内有其他团队同址的读取比例 |
|---|---:|---:|---:|---:|
| DT Q32，全团队同序 | 65,536 / 2,048 | 0.528 | 289 / 418 | 96.11% / 99.12% / 99.82% |
| PR Q32，同候选、分段错相 | 65,536 / 2,048 | 0.831 | 318 / 696 | 7.59% / 28.90% / 73.82% |
| DT Q64，各行变换候选 | 131,072 / 17,408 | 1.127 | 579 / 869 | 4.68% / 17.37% / 46.72% |

密度以从首个到末个 folded 发起的周期数为分母。Q32 两端各有 64,384 条单 burst 和 576 条双 burst 描述符。DT 有 32 个对齐的完整行团队；PR 有 28 个 36/37-tile 团队，静态同序相位团队对占 1/27。PR 的读取密度更高、近同时同址访问更少。Q32 需要的实际设备总窗从 84.792 µs 降至 59.568 µs。该对照同时改变了芯片和分核，缺测 L2 命中、bank 排队及 HBM 实际传输字节。

表中“同址”按每个请求是否存在至少一个跨团队同址伙伴计数。另一个可重绘指标以桶内所有跨团队请求对为分母，512 周期的同址请求对比例在 DT Q32、PR Q32、DT Q64 分别为 5.816%、0.0583%、0.0292%。两种指标分母不同。静态 `candidate_order_overlap` 则对候选顺位计数，无法直接等同于任一动态指标。

## 同一核的第一行与第二行

旧 DT Q64 中每个团队整齐执行两行。每个 AIV 在首行发起 1024 个 record，随后进入第二行。归属按 AIV 有序源指令序列与原厂 tile 日程划分，各 AIV 的 record 数均与元数据吻合。两个 burst 的单条描述符均落在同一片段。下表给出 32 个团队合计。

| DT Q64 | 发起区间（µs） | record 数 | 发起密度（record/周期） | 每条描述符 record 数 | 128 / 512 周期内有其他团队同址的读取 |
|---|---:|---:|---:|---:|---:|
| 每团队第一行 | 5.399–46.901 | 65,536 | 0.957 | 1.131 | 3.38% / 14.31% |
| 每团队第二行 | 44.101–75.869 | 65,536 | 1.250 | 1.155 | 5.86% / 20.11% |

相同 record 数下，第二行发起密度高 30.6%，每条描述符承载的 record 仅多 2.1%。单队统计也显示密度由中位 0.0340 升至 0.0471 record/周期。部分团队已开始下一行时，其他团队仍在第一行。两条 MMAD 的单队跨行间隔中位 5507.5 周期，而每个 AIV 两行边界的末、首 record 发起间隔中位为 4081.5 周期。两个中位来自不同指令链，无法将差值直接解释为预取省下的周期。源码允许预取下一行最多四个槽，这与地址端和计算端出现不同交接节奏相符。[源码、分核和 MMAD 取参](v113_mechanism.md)

PR Q32 首片与后续片的 512 周期同址比例为 29.28% 与 28.56%；两类片段长短不同，且在设备时间上大范围重叠。其发起密度（只统计本类 operand）分别为 0.478、0.561 record/周期。该样本有 27 行跨团队归并，不能当作全部团队连续两条完整行的观测。

## 哪一段还少估

按真实布局给 v1.13 定价，在同一模型团队关键链上还原“首次 MMAD 发起”和“最后一条 MMAD 退休”的预算。CA 一栏取全设备实际最早/最晚 MMAD，该设备端关键核可在阶段间变化。下表的正值是 CA 比模型多出的时间。三项差额相加等于该窗总残差。

| 旧窗 | 启动至首次 MMAD（µs） | 首发至末退休（µs） | 末退休至全部退出（µs） | 合计 CA−模型（µs） |
|---|---:|---:|---:|---:|
| DT Q32 | +1.381 | +0.530 | +1.306 | +3.216 |
| PR Q32 | −1.126 | +3.658 | +1.937 | +4.469 |
| DT Q64 | 0.000 | +5.054 | +0.873 | +5.927 |

DT Q32 的中段与建模接近，约 2.69 µs 的差额来自启动与排空。PR Q32 的行片长短与跨核归并清楚可见，尽管 512 周期的同址伙伴比例已达到 28.90%，静态相位近似和每团队中位间隔仍未完全覆盖实测中段。DT Q64 第二行的发起明显加快，模型已分别计入首行、续行和行交接；余下 5.054 µs 集中在主体区间，里面同时包含不同核首发时差、慢核、环槽等待与发起气泡。仅凭源地址和收到指令的时间戳无法分配各自的独立代价。此分析复用 v1.13 冻结前的三次 CA，零新增 CA，也没有据此更新系数。

使用 Python 3.10+ 从仓库根目录运行 `PYTHONPATH=src:. python -m calibration.candidate_indexer.v113_mechanism_traffic --jobs 3`。旧 trace 体积较大，仓库内保留汇总 JSON。若只核对冻结模型的阶段分解，可传 `--reuse-traffic` 复用已有统计。
